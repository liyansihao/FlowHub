# 榜单优先、种子补位

基于唯一生产提交 `e555cbbea43a066a5bd2386d00c40cc5c1b59400` 的隔离变更。
当前为开发候选，未部署、未启用、未合并 main；不使用 main 的性能修复分支替代完整生产组合。

## 行为与边界

1. 来源平台近 28 天销量大于 0 的榜单商品优先进入现有准入。新种子也可用该商品自身的月销量证据。不是要求自己的店先出单；榜单均价仍为统计值，不写成挂牌价。
2. 榜单没有可准入的新品时，沿用原种子扩展候选；后续榜单发现新品，下次新准入恢复榜单优先。已有补资料、审核、发布、回查任务不抢占或重排，店铺轮转不改。
3. 在现有 source loop 中，每次最多读取一页榜单；每个类目约 6 小时重读榜首页，其余页从持久化游标继续。完成一轮后下一轮重新遍历。类目轮流调度；未配置类目时沿用来源筛选中的类目，仍为空则读取总榜。沿用现有 ERP 全局请求节奏，无第二个发布服务。
4. 空榜只等待下一次刷新；网络失败保留游标并退避重试。短页不等于榜单耗尽，需要结束元数据或明确空页。种子候选积压不阻止榜单刷新；榜单待准入商品达到 2,000 时暂停向后翻页，仍定期回查榜首页。
5. 证据观测时间和服务方数据更新时间分别保留，采用已有来源筛选的 7 天新鲜度口径。旧报表重新拉取不会变成新销量；较新的零/未知销量不退回采用旧正销量。
6. 首次启用时，持久化记录当时已有种子身份。历史种子、历史发现任务、已采候选和在途任务保留。新成功上架商品若无自身销量证据，进入单 SKU 销量查询，查到正销量才加入新种子；不继承父种子的销量。不删除历史记录或修改人工决定。
7. 新独立榜单使用 `flowhub-sales-ranking-v1`，保留真实 SKU、卖家、接口、查询条件、销量、时间和证据摘要。没有假造同店根种子。缺少原审核要求的价格、重量等事实时仍走既有补资料流程。
8. 原同款、成本绑定、利润、邮政 500g、定价、库存目标、去重、禁售/人工下架、跟卖后端和 Offer 身份规则保持。收藏归档仅增加对新来源凭证的识别，仍要求已上架、无在途租约、线上 Offer/库存确认、两份持久归档和原有未知写入回查；新凭证随商品原文归档，不虚构 root_seeds。

## 影响文件

- `flowhub/ranking_sources.py`：榜单、销量证据、新种子资格、分页与历史种子快照。
- `pipeline_modules/source_loop.py`、`admission.py`、`other_sellers.py`：接入原循环和准入；旧开关关闭时继续原来源逻辑。
- `plugin_comparebot.py`、两处 bridge 与 `ranking-source-policy.mjs`：识别新的真实来源契约。
- `pipeline_modules/favorite_cleanup.py`：使榜单来源能沿用既有收藏归档保护，避免长期占满收藏。
- 新增来源回归测试；原跟卖测试中增加榜单来源贯穿导入与库存回查的场景。

## 受控启用与回退

配置文件位于所选数据库目录的 `ranking-source-policy.json`，示例：

```json
{"enabled": true, "owner": "实际租户ID", "max_pending": 2000}
```

可用 `categories` 指定已有业务范围内的类目 ID 数组。不增加其他业务范围。生产启用前核对唯一基线和当前差异、保存受保护账本摘要、按既有受控部署流程切换唯一主服务并记录时间，再写入该配置。源码切换和配置启用不复制、覆盖或重建业务数据库。

关闭 `enabled` 后停止新的榜单准入/刷新，原在途任务继续依赖本版来源契约完成。保留本版回查与来源识别，不能直接降级丢弃新的在途记录；已完成的游标、资格证据和历史种子快照不清除，也不会因重新启用把新种子重新算作历史种子。

## 验证

所有修改及测试在隔离工作树和临时数据库中进行；接口调用使用模拟响应，没有试发真实商品。测试结果与生产只读检查见 `docs/ranking-source-validation.md`。
