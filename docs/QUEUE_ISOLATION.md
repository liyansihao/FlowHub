# 正常上架优先与异常隔离

开启：生产 data/queue-isolation.json 设置 `{"enabled":true}`。不开启时保持旧清理策略。关闭开关只停止新隔离与自动回查，不自动释放已隔离任务；恢复应沿原发布意图检查，不能删除记录后重建。

每分钟扫描一次，跳过运行中的 SKU 租约并尊重模块暂停：缺资料失败 3 次或等待 2 小时，收藏重试耗尽，发布进入人工核查，或远端等待 2 小时，将本地调度状态改为 quarantined。保留原商品、收藏、发布记录、幂等键、提交/库存意图及审核时间，不删除远端数据。每次隔离持久保存完整原队列恢复凭据。其他明确平台错误本就进入 needs_review，不再占正常队列。

隔离通道每分钟最多检查一个任务，同一任务正常情况下 6 小时后才再查；凭证/预算推迟至少 15 分钟。只允许官方仓库、原 offer 查询、库存回查三个只读接口，传输层拒绝上架、改库存等写请求。无官方凭证或无原发布记录的任务保留待处理，不走 ERP 高成本补采。

请求预算按启用后的官方实际网络请求累计计数，缓存不提供额度。隔离请求最多占官方正常+隔离请求预算的 10%；正常待执行队列不少于 8 条时收紧到 5%。预算在数据库中保存，重启不重置；未实际发送的预留也保守扣减。正常待处理任务为空时，允许借用空闲时间，每分钟最多 3 次只读请求，避免没有新任务时永远无法确认旧任务完成；一旦正常任务出现立即恢复比例限制。空闲请求独立计数，不产生预算额度。该比例是有正常任务时的官方请求预算，**不是整个系统 CPU、所有 ERP/飞书请求或墙钟耗时比例**。

只读检查确认 selling 且目标仓 present=99 后，核对原发布记录未变化、无待执行下架操作，直接完成原本地 journal、发布记录和队列收尾，不重新发布或写库存。原 offer 已明确准备销售且原 journal 为 reconciling/sync_pending 超时、仍在原写入期限内时，可一次性释放回原受保护流程，给予 30 分钟恢复机会。检查本身不写库存；原流程继续校验审批、来源、飞书明确下架及目标身份。无法确认的 submitting/stock_pending 意图不重置、不重发。一次恢复仍未完成则再次隔离，停止自动反复激活。

官方状态兼容仅将 price_sent + moderate_status=approved + validation_status=success + is_created=true + 正 SKU + 未归档 + 无 issue 的组合转为 ready_to_sell；绝不当成已可售。图片/属性警告仍保守保留，没有一概忽略。

查看：`python scripts/report_queue_isolation.py --data /path/to/data`。管理卡显示“已隔离 · 不占正常上架队列”；原任务和证据继续保留。
