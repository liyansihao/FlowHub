## 本轮改动

1. 在补齐模块发出远程请求之前，优先读取按 owner、ERP 账号和 SKU 绑定的已完成本地草稿。沿用六小时缓存窗口，要求精确 SKU、单变体、完成状态；保留原采集时间。只补缺项，后续原测算同步和发布守卫继续执行。
2. 已经审核通过、等待完整发布资料的任务，在退避到期后仍优先于新候选获取资料。未到 due、活动租约、暂停状态与总处理名额限制保持有效。
3. 相同账号、相同参数的并发资料 GET 合并；仅草稿采集换算所用汇率保留 60 秒缓存，不缓存或续期商品报价。连续三次连接失败后，该账号对应读取接口退避 60 秒，其他接口继续执行。
4. 草稿采集的读取接口也采用按账号和接口隔离的失败退避，避免旧异常商品逐件占满超时。写入仍走原始一次性记录，不经过读取缓存或自动重发。

没有提高并发、改变利润/售价门槛、扩大库存或重置不确定发布记录。完整资料若改变关键测算输入，仍须重新测算。

## 实测口径

只读脚本 `scripts/measure_throughput_window.py` 按固定时间窗口统计：

- 每个发布记录第一次进入 `stock_verified`；同一记录重复回查不重复计数。
- 审核完成到第一次库存确认的耗时中位数及样本量。
- 发布请求的排队/网络耗时、错误事件和缓存/合并数。
- 补齐执行及资料完整次数、本地草稿复用次数。

小时速率仅是窗口内数量折算，不是持续一小时实测。新旧窗口不是同一批商品的随机对照，商品难度与上游波动可能影响结果。完整数据在 `baseline-window.json`、`after-window.json`；实测结果如下。
