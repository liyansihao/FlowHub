# 官方发布切换后的三处吞吐修复

用户要求修复补资料、审核衔接和属性校验三个堵点。本次继续 official_only，不恢复毛子发布，不改变全局 ERP 2500ms 限速，不重放已提交任务。

## 定位及修改

1. 属性值 `2` 导致官方 `/attribute/values/search` 返回 400：服务要求搜索词至少两个 Unicode 字符。直发校验改为按源资料已有 dictionary_value_id 调用 `/attribute/values`，同时严格比对返回 ID 与文本；不补空格、不猜值。来源映射的废弃字典回退搜索也不发送单字符。真实 5 条原错误任务只读预检全部通过，原审核可复用。
2. 原审核来源参考价是 RUB，补资料沿用已批准的 CNY 上架价时被误判为改价。现在仅在原审批仍有效、售价数值/币种/决定时间/嵌套原始参考价全部精确匹配时复用；不重新换汇，不刷新审批时间。真正改变尺寸、售价、身份或过期仍需重新测算。同步失败不再删除审核，先加密归档；已有有效上架授权的任务继续完整测算，不误转仅同款核对。
3. 配置已经有两个补资料 worker，但第二个依赖旧毛子发布 StepTransport 的健康样本。切官方后没有足够样本，导致它实际闲置。现在依据补资料自身最近 2–3 次成功、耗时及错误判断是否允许第二个 worker，异常自动退回一个。两个 worker 分别优先处理发布补资料和新来源测算资料，可互相补位，继续共用原 SKU 租约。已有官方资料积压不再吃掉全部新来源预算；积压期间最多额外接入 8 个未齐测算资料的新任务，主并发和总预算仍受限。

## 丢失人工确认的修复

原故障删除完整审核后，独立身份复核覆盖了一批用户此前确认的同款结论。`human_reviews` 仍保留真实原始操作凭证。恢复时要求当前仍是同一条 list 授权、没有发布记录/历史 job/禁处理/活动租约，最新人工动作为 approve，并严格核对原 SKU、卖家、标题、图片、已知变体、类目、包装及已有属性；新增资料允许补全，已知属性变化及后续明确品牌/型号冲突阻止恢复。人工确认时间沿用原凭证，不创建新的人工审批。

恢复只回到原同款确认及原 list 请求，仍由现有流程重新检查当前售价/利润/物流、官方额度、资料、防重和库存。恢复入口也改用官方额度，去掉新官方任务重新进入网站上架准备时的毛子导入记录依赖。旧发布和下架仍按原记录处理。

`scripts/recover_repair_regressions.py` 默认只读，`--apply --limit N` 分批恢复。每次变更加密保存原队列、审核、管理操作；原请求 ID 保持不变。一次只读扫描发现 60 条可恢复原人工确认、6 条单字符校验错误；1 条包装发生变化保留待复核。数字会随旧 worker 运行变化。

## 验证

测试覆盖单字符字典、ID/文本不一致、CNY 审批链保持与伪造价格/时间拒绝、审核归档、list/unlist 授权差异、双补资料租约并行、无旧 ERP 流量时第二 worker 开启、失败/陈旧健康证据退避、官方补资料积压下新来源预算上限、人工凭证恢复及身份/包装/属性/拒绝/冲突阻止恢复。
