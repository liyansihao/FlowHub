# FlowHub 三模块流水线：40 件/小时目标

分支：`codex/modular-pipeline-40ph`。40 件指 60 分钟内新商品在目标嘉兴邮政仓回查可售且库存 99，不以入队、测算通过、提交成功代替。当前仅能证明改造与小批运行结果，达标必须由真实窗口验证。

## 模块边界

| 模块 | 输入 | 输出与职责 | 实现 |
|---|---|---|---|
| 种子来源 | 已授权种子、来源店铺与分页游标 | 去重来源、来源关系、采集时间、商品资料、缺项及补采状态 | `pipeline_modules/seed.py`，复用 SourceAcquirer / SourceLibrary |
| DINO／千问审核 | 完整来源资料 | 1688 候选、DINO 分数、千问结论、精确采购报价、利润证据 | `pipeline_modules/review.py`，复用 compareBot 与原测算模块 |
| 上架 | 通过审核的资料、用户授权、绑定店铺与期限 | 毛子发布意图、平台回查、嘉兴邮政库存、可售证据 | `pipeline_modules/publication.py` / plugin_publication |

资料不齐留在补采环节；未确认配送／跟卖可以按用户逐 SKU 授权放行，但不伪造 FBS 或跟卖许可。明确禁止、品类限制、人工反馈、飞书待下架、重复来源、采购报价绑定和利润门槛继续检查。

## 改动

1. 补价 1 个工作通道，审核 2 个，新发布 2 个，回查 2 个。审核和上架互不阻塞；库存和平台回查有保留容量。每类上限 4，避免无边界请求。
2. 数据库原子领取，租约每 30 秒续期，崩溃 120 秒后恢复；旧租约不能覆盖新任务结果。正常取消释放租约。未知写入仍依靠原毛子意图日志回查，不重新提交。
3. 使用 SKU 锁和目标店铺锁。同 SKU、同店铺不重叠，不同店铺可以并行推进。全局维护锁可等待全部在途操作退出再重载。原毛子共享 API 限速继续有效。
4. DINO 和审核子进程常驻，DINO 权重与向量缓存复用。千问密钥按单次调用传递、完成后清除；子进程输出不打印密钥。调用失败仍不批准上架。
5. 上架复用审核绑定的完整插件资料，不再为核对相同包装数据创建第二份毛子采集草稿。过期、身份不符、缺属性的资料不能走快速路径；包装尺寸和重量仍与测算一致性比较。
6. 每次队列操作记录所属模块、SKU、起止时间、状态和原因；只统计可售且库存回查通过的唯一来源商品。

## 操作与回滚

```
.venv/bin/python -m flowhub.pipeline_modules status
.venv/bin/python -m flowhub.pipeline_modules pause seed
.venv/bin/python -m flowhub.pipeline_modules pause review
.venv/bin/python -m flowhub.pipeline_modules pause publication
.venv/bin/python -m flowhub.pipeline_modules resume publication
```

暂停停止领取新操作，在途操作会完成；不强杀写入。种子模块的开关用于主 worker 的来源采集，独立旧 seed_pipeline 仍使用其 PAUSE/DEADLINE 文件。

本机 `data/pipeline-v2.json` 开启新调度。回滚为 `enabled:false` 后，在独占 `plugin-publication.lock` 的空闲边界重启 worker 即可；发布日志、路由、去重记录都保留，不删除状态，不重复发布。单进程旧队列仍兼容新的租约表。

期限来自每件商品绑定的 route/record，调度重启不延长期限。测试窗口结束停止发布和库存写入；已发请求后续只计回查证据，不能混进截止前成功数。

## 验收

- 并发测试：同 SKU 不重复领取；同店铺不重叠；不同店铺并行。
- 恢复测试：暂停、取消、租约过期、旧工作进程晚到结果不能覆盖新租约。
- 调度测试：慢审核不阻塞新发布和库存回查；库存回查优先。
- 业务测试：未知权限严格限定；明确禁止、必填资料缺失和利润不合格仍拦截。
- 真机审核测速：冷启动同 SKU 13.31 秒；首次常驻 10.72 秒、DINO 分数相同；后续两个不同 SKU 8.15 / 7.79 秒。样本少且图片内容不同，不能推断整条流水线同比提升。
- 生产基线与后续记录存入 `reports/modular-40ph-20260912/`，只操作原已授权补充批次，不延长其截止时间。

达到 40 件/小时需要审核通过的资料供给足够、单件平均共享 API 占用时间小于 90 秒，并且平台审批/商品质量允许。并发减少等待，不能绕过共享 API 限速或保证平台审核结果。

## 2026-09-12 验收补充与尚未解决的供给问题

全链路单样本审核 11.47 秒，其中 DINO 搜索 10.82 秒、利润 0.53 秒、复核阶段 0.13 秒。这个样本属于高相似度小商品自动通过，并未实际调用千问，不能把 0.13 秒当作千问接口速度。

真实队列暴露了另一问题：许多商品虽然最近完成测算，使用的来源售价仍是更早采集的，等待后超过 6 小时。原业务桥将其合并成 `human_feedback_blocked`。已经加入发布准备前的价格时效检查，过期进入 `needs_fields`，明确显示 `fresh_sale_price`；不再把价格过期解释成人工否决。70 条旧错误已重新分类，原原因保存在诊断报告中。

通过毛子直连对 某个精确 SKU 复查，返回 `update_sales=true`、无 avgPrice/seller。不能据此补出新价格，也不能人为更新旧价格的采集时间。过期商品已接入独立补价通道：每 5 分钟最多重查一次毛子直连，必须精确绑定 SKU、卖家且接口确认数据已更新，才能保存新价格并重新审核。路由到期不再发补采请求。尚未提交的旧计划仅在售价、采购价、供应商和包装均未改变时更新审核证据；发生经济条件变化则单独标记需要重建计划，不偷偷修改原发布意图。本次没有启动 Chrome，也没有改用榜单。

因此本分支完成了模块拆分、并行调度、常驻审核、资料复用、并发与恢复保护，但 **40 件/小时尚未验收通过**。这轮存量已审商品不构成种子→审核→上架的完整新批次吞吐证明。不能用队列操作次数或按短时数据外推宣称达标。


## 后续纠正

上述“70 条价格过期需要补价”的结论后来确认混淆了参考竞品报价与已批准上架售价。72 个商品已有完整资料和有效定价，已按原批准定价恢复；真正缺项才进入毛子逐字段补采。参见 [毛子补资料修复](maozi-field-repair.md)，不再把这批误拦截归因于毛子缺少商品资料。
